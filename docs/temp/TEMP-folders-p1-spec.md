## 4. Схема

```sql
CREATE TABLE folders (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    org_id      UUID NOT NULL REFERENCES organizations(id) ON DELETE RESTRICT,
    owner_id    UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    parent_id   UUID REFERENCES folders(id) ON DELETE RESTRICT,
    section     TEXT NOT NULL CHECK (section IN ('library', 'my', 'students')),
    kind        TEXT NOT NULL CHECK (kind IN ('folder', 'student')),
    student_id  UUID REFERENCES students(id) ON DELETE RESTRICT,
    name        TEXT NOT NULL,
    depth       INT  NOT NULL CHECK (depth BETWEEN 0 AND 4),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT folders_kind_student_chk CHECK (
        (kind = 'student' AND student_id IS NOT NULL AND section = 'students') OR
        (kind = 'folder'  AND student_id IS NULL)
    )
);

CREATE INDEX folders_org_section_parent_idx ON folders(org_id, section, parent_id);
CREATE INDEX folders_owner_section_parent_idx ON folders(owner_id, section, parent_id);
```

```sql
ALTER TABLE packs
    ADD COLUMN folder_id         UUID REFERENCES folders(id),
    ADD COLUMN library_folder_id UUID REFERENCES folders(id),
    ADD COLUMN published_at      TIMESTAMPTZ,
    ADD COLUMN age_min INT CHECK (age_min IS NULL OR age_min BETWEEN 3 AND 18),
    ADD COLUMN age_max INT CHECK (age_max IS NULL OR age_max BETWEEN 3 AND 18),
    ADD COLUMN difficulty TEXT CHECK (difficulty IS NULL OR difficulty IN ('easy','medium','hard')),
    ADD COLUMN goals TEXT[] NOT NULL DEFAULT '{}',
    ADD COLUMN notes TEXT NOT NULL DEFAULT '',
    ADD CONSTRAINT packs_age_range_chk CHECK (age_min IS NULL OR age_max IS NULL OR age_min <= age_max),
    ADD CONSTRAINT packs_published_chk CHECK ((library_folder_id IS NULL) = (published_at IS NULL));
```

### Почему `depth` колонкой, а не рекурсивным запросом

Ограничение — пять уровней. При создании `depth = parent.depth + 1`, проверку делает `CHECK`, лишнего запроса нет. Рекурсивный обход остаётся только в `move`, где он всё равно нужен, чтобы поймать перемещение папки в собственного потомка. При перемещении пересчитывается `depth` всего поддерева — один `UPDATE` с рекурсивным CTE.

Перед перемещением проверяется максимальная относительная глубина всего поддерева. Проверки только новой глубины корня недостаточно: потомки могут выйти за предел `depth <= 4`.

### Инварианты, которые проверяет service

Их нельзя выразить обычным `CHECK`, потому что они сравнивают несколько строк и таблиц:

- дочерняя и родительская папки имеют одинаковые `section` и `org_id`;
- в `my` и `students` у родителя и ребёнка совпадает `owner_id`;
- в `library` автор создаёт и перемещает папки только внутри собственного дерева; `admin` может работать со всем деревом;
- папка `kind=student` ссылается только на ученика своего `owner_id`;
- `folder_id` набора указывает на папку `my` или `students` того же владельца и организации;
- `library_folder_id` указывает только на папку `library`;
- пользователь не может создать или переместить объект в чужое дерево;
- move папки и пересчёт `depth` выполняются в одной транзакции с блокировкой изменяемого поддерева;
- конкурентные delete/move/create не обходят проверку пустоты и глубины.

### Чего в схеме намеренно нет

- **`deleted_at`** — удаляем только пустые папки (§6), восстанавливать нечего.
- **уникальность имени папки** — требования нет ни в фич-листе, ни в дизайне. Две папки «Животные» рядом — это проблема пользователя, а не инвариант базы.

По auth-спеке регистрация создаёт личную организацию. `users.org_id` пока остаётся nullable ради совместимости с существующей схемой и данными, но P1 API работает только для пользователя с организацией. Auth-регистрация обязана создавать организацию в той же транзакции; отдельная auth-миграция позже делает backfill существующих пользователей и закрепляет `users.org_id NOT NULL`.

`org_id` ограничивает **запись**: создание, перемещение и правку объектов в чужом дереве. Чтением он не управляет — библиотека видна всем авторизованным пользователям поверх организаций (§6). Фильтр по `org_id` в library-выборках сломает общий доступ.

## 5. API

```
POST   /api/v1/folders                      создать папку или папку ученика
GET    /api/v1/folders?section=&parent_id=  список; без parent_id — корень раздела
GET    /api/v1/folders/{id}/contents        смешанный список: папки + наборы
PATCH  /api/v1/folders/{id}                 переименование
POST   /api/v1/folders/{id}/move            смена родителя
DELETE /api/v1/folders/{id}                 только пустую

POST   /api/v1/packs/{id}/publication       опубликовать в library_folder_id
DELETE /api/v1/packs/{id}/publication       снять публикацию

POST   /api/v1/students                     завести ученика
GET    /api/v1/students                     картотека
PATCH  /api/v1/students/{id}
DELETE /api/v1/students/{id}
```

Плюс CRUD наборов из #92, дополненный `folder_id`.

`GET /folders/{id}/contents` возвращает папки и наборы одним упорядоченным списком с discriminator `type=folder|pack`. Контракт фиксирует одинаковые поля сортировки, стабильный tie-breaker по `id`, параметры pagination и допустимые `sort`/`order`. Это позволяет сортировать и листать содержимое целиком, без склейки двух ответов на фронте.

Для `GET /folders` явно различаются отсутствующий `parent_id` (корень указанного `section`) и переданный UUID. Если передан родитель, backend проверяет совпадение `section`, организации и прав доступа.

### Кнопка «Создать» (4.1.1)

Бэкенду делать нечего. Это выпадающий список, который дёргает `POST /folders`, `POST /folders` с `kind=student` и `POST /packs`. Отдельной задачи нет.

### Корневые разделы (4.1.5)

Не сущности в БД, а три значения `section` (`architecture-decisions.md §9`). Отдельного endpoint'а нет.

### Папка ученика (4.1.3)

Ученик заводится отдельно через `POST /students`, папка на него ссылается через `student_id`. Автосоздание ученика из папки невозможно: `students.email_encrypted` объявлен `NOT NULL`, пустую запись туда не положить.

## 6. Правила доступа

| section | читают | создают | правят и удаляют |
|---|---|---|---|
| `my`, `students` | владелец | владелец | владелец |
| `library` | все авторизованные | `defectologist`, `admin` | автор или `admin` |

Обращение к чужой папке в private-разделах возвращает **404, а не 403** — 403 подтверждает, что объект существует. Папки `library` публичны для авторизованных пользователей, поэтому для запрещённой операции над видимой чужой папкой допустим `403`.

Публикация набора в библиотеку — ссылка, не копия (`architecture-decisions.md §10`). Удаление опубликованного набора возвращает `409`, пока публикация не снята.

При чтении library endpoint возвращает только наборы с заполненными `library_folder_id` и `published_at`. Чтение библиотеки глобальное для всех авторизованных пользователей и не фильтруется по `org_id`; сам `org_id` остаётся атрибутом владельца и границей записи. Наличие обычного `folder_id` в пользовательском дереве не делает набор публичным. Публиковать и снимать публикацию может автор набора или `admin`; автор публикует только в собственную library-папку, `admin` — в любую. Создавать папки библиотеки могут `defectologist` и `admin`, править и удалять — автор папки или `admin`.

Повторный `POST publication` в ту же папку идемпотентен. Попытка опубликовать уже опубликованный набор в другую папку возвращает `409`: сначала публикацию нужно снять. Повторный `DELETE publication` возвращает `204`.

## 7. Критерии приёмки

Формулировка «работает дерево папок» непроверяема. Ниже — то, что должно быть тестом.

**Папки**

- создание папки в корне раздела: `depth = 0`, `parent_id IS NULL` → `201`
- создание шестого уровня вложенности → `400`
- перемещение папки в собственного потомка → `409`
- перемещение поддерева пересчитывает `depth` у всех потомков
- перемещение поддерева, у которого хотя бы один потомок окажется глубже 4 → `400`
- создание или move под родителя из другого `section`, `org_id` или чужого private-дерева запрещено
- обращение к папке чужого пользователя → `404`
- удаление папки с содержимым → `409`; удаление пустой → `204`
- конкурентные создание дочернего объекта и удаление родителя не приводят к каскадной потере данных
- `kind=student` в разделе `my` → `400`
- `kind=student` с несуществующим `student_id` → `400`
- `kind=student` с учеником другого дефектолога → `404`

**Наборы**

- создание набора кладёт валидный пустой `config` Linka 2.0
- набор без `folder_id` не создаётся
- move набора в чужую папку или в недопустимый section запрещён
- публикация возможна только в папку `section=library`
- library contents не показывает неопубликованные наборы
- повторная публикация в ту же папку идемпотентна, в другую → `409`; копия набора не создаётся
- снять публикацию может автор или `admin`; набор остаётся в исходной пользовательской папке
- удаление опубликованного набора → `409`
- `age_min > age_max` → `400`

**Ученики**

- создание ученика без email → `400`
- список возвращает только учеников текущего дефектолога
- delete — soft-delete по правилам AB-47; если у ученика есть папка, операция возвращает `409`

**Общее:** unit/handler-тесты входят в AB-42a/AB-42b/AB-43′/AB-47. AB-59 содержит только сквозные интеграционные и конкурентные сценарии на testcontainers по паттерну `internal/auth`, включая upgrade миграций со схемы текущего `main`.
